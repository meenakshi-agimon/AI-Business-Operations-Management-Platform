# Data Cleaning Documentation — Employee Management Module

## Overview
This document describes the cleaning process applied to `Business_Operation.csv`,
the raw synthetic dataset for the Employee Management module. It supports the
AI-based task allocation feature, following the allocation logic:

`Required Skill → Skill Match → Availability → Workload → Recommended Employee`

**Output used:** `Business_Operation_ml_ready.csv` — this is the dataset actually
used going forward. All cleaning steps below are the pipeline that produces it.

## Input
- **Raw file:** `Business_Operation.csv`
- **Shape:** 50,250 rows × 25 columns
- **Source:** Synthetic data generated by teammate, with intentional missing
  values, duplicates, and formatting inconsistencies for the cleaning exercise

## Protected Fields
The following fields must never be renamed or removed, since the existing
Employee Management logic depends on them by exact name:
- `employee_id`
- `skills`
- `required_skill`
- `availability_status`
- `workload_percentage`

## Cleaning Steps

1. **Remove exact duplicate rows**
   250 fully duplicate rows were dropped (50,250 → 50,000 rows).

2. **Normalize text casing and spacing**
   Categorical columns (`department`, `job_role`, `availability_status`,
   `task_priority`, `task_status`) had inconsistent casing/spacing (e.g.
   `'Marketing'` vs `' marketing '`). Standardized via trim + Title Case.

3. **Fix known abbreviations and acronym mangling**
   - `"Engg"` → `"Engineering"`
   - Title Case broke acronyms (`HR` → `Hr`, `IT` → `It`); corrected back to
     `HR` / `IT` after normalization.

4. **Backfill employee-level attributes from the employee's own records**
   `department` and `job_role` are properties of the employee, not the task.
   Where missing, these were filled using the employee's own most common
   value across their other rows (`employee_id` groupby), before falling
   back to `"Unknown"` only if no valid value existed for that employee at all.

5. **Cap out-of-range workload values**
   500 rows had `workload_percentage` above 100; capped at 100.

6. **Handle remaining missing values, by field type**
   - Categorical/identity fields (`availability_status`, `task_priority`,
     `task_status`, `required_skill`) → filled with `"Unknown"`
   - Free-text fields (`employee_name`, `task_title`, `task_description`,
     `skills`) → filled with `"Not specified"`
   - Numeric fields (`experience_years`, `workload_percentage`,
     `performance_score`, `estimated_hours`, `hours_logged`,
     `progress_percentage`) → filled with the column median

7. **Verify data integrity before ML transformation**
   - Re-checked for genuine per-employee department conflicts (excluding
     `"Unknown"` placeholders): 0 found
   - Confirmed all 5 protected columns are still present and unrenamed

8. **Build ML-ready features**
   - Split the comma-packed `skills` column into a list per employee
   - Added `skill_match` (1/0 flag: does the employee have the task's
     `required_skill`)
   - One-hot encoded individual skills (`skill_sql`, `skill_django`, etc.)
   - One-hot encoded categorical columns (`department`, `job_role`,
     `availability_status`, `task_priority`, `task_status`, `required_skill`)
   - Dropped free-text and identifier columns not useful as model inputs
     (`employee_name`, `email`, `task_title`, `task_description`, `skills`,
     `task_id`, `hire_date`, `task_start_date`, `task_deadline`)

## Output

| File | Description |
|---|---|
| `Business_Operation_ml_ready.csv` | Fully cleaned and encoded, ready for model training. No missing values, no duplicates, all categorical fields numeric. |

## Validation
- `skill_match` correlates with `recommended_employee` as expected: employees
  with a matching skill are recommended significantly more often than those
  without — confirms the feature carries real signal, not noise.

## Known Data Notes (for the team)
- `hours_logged`, `progress_percentage`, and `allocation_score` appear to
  reflect information generated after or alongside the allocation decision.
  Using them as model **input features** to predict `recommended_employee`
  risks data leakage. Recommend confirming with the teammate who built the
  labels how `allocation_score` / `recommended_employee` were generated
  before finalizing model inputs.
- `experience_years` and `performance_score` show weak correlation with
  `recommended_employee` in the current synthetic data, despite experience
  being named in the allocation flow — worth validating whether this is
  intentional.

## How to Reproduce
Run the accompanying notebook (`Employee_Data_Cleaning.ipynb`) or script
(`clean_business_operation.py`) in the same folder as the raw CSV. Both
read `Business_Operation.csv` (never modified) and write
`Business_Operation_ml_ready.csv`. Re-run any time the raw data is updated.
